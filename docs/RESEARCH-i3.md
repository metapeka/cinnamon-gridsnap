# Почему любят i3 и что из этого взять GridSnap

Записано 19.11.2026 по итогам практического разбора (сеанс i3 поднят и проверен на этой машине;
полный контекст — в блокноте настроек `~/thinkrail/ws_settings2/notes/window-tiling.md`).

## В чём фишка i3

1. **Окна всегда занимают экран целиком.** Нет перекрытий, нет «поймай заголовок, подвинь, подгони».
   Раскладка пересчитывается сама: закрыл окно — соседи расширились.
2. **Всё с клавиатуры.** Контекст не теряется: фокус влево-вправо, перестановка соседей, столы, вкладки —
   всё хоткеями. Мышь становится необязательной, а не главной.
3. **Детерминированность.** Ты знаешь, куда попадёт окно и на каком столе оно живёт. Забытых окон нет:
   они не «свернулись в панель», а лежат на своём столе.
4. **Воркспейсы — это раскладки, а не список окон.** Десять независимых наборов окон, именованных,
   с правилами «что куда открывать».
5. **Конфиг как код.** Один текстовый файл: хоткеи, правила, автозапуск. Версионируется, переносится
   на новую машину за минуту, объясняется коллеге ссылкой на dotfiles.
6. **Композиционность.** i3 только управляет окнами — панель, лаунчер, уведомления, обои подключаются
   отдельно. Ничего лишнего не работает: ~15 МиБ RSS против ~250 МиБ у шелла DE.
7. **Мощные примитивы:** сплиты по горизонтали/вертикали, вкладки и стопки в контейнере, плавающий слой
   для диалогов, scratchpad (окно, которое вызывается по клавише), `marks`, критерии по классу/заголовку,
   `assign` и `for_window`.
8. **Управляемость из скриптов.** `i3-msg` даёт IPC: можно писать свои команды, интеграции, варианты
   поведения — то, из чего у людей вырастают личные «де-факто DE».
9. **Предсказуемая производительность.** Никакой анимации и композитинга — нет просадок на слабом
   железе и в удалённых сессиях.

## Чем это принципиально отличается от GridSnap

| | GridSnap (зоны) | i3 (динамический тайлинг) |
|---|---|---|
| Модель раскладки | зоны фиксированы, окно кладётся **по команде** | окна **сами** заполняют экран по дереву |
| Кто решает | человек, каждый раз | WM, по правилам |
| Перекрытия | возможны | невозможны в тайловом слое |
| Реакция на события | нет (только по хоткею) | автоматическая (открыл/закрыл — пересобралось) |
| Воркспейсы | родные Cinnamon: набор окон без раскладки | 10 независимых раскладок + правила `assign` |
| Вкладки/стопки | нет | есть |
| Панель, апплеты, десклеты, меню, трей | **всё на месте** | нет, собирать из чужих частей |
| Порог входа | нулевой (уже работает) | новый быт: хоткеи, конфиг, свои привычки |
| Где живёт код | поверх EWMH muffin | сам является оконным менеджером |

**Вывод.** i3 не «лучше красивее» — он про автоматизм раскладки и отсутствие ручной возни. GridSnap
не конкурирует с ним в динамике, зато даёт то, чего в i3 нет: привычный рабочий стол целиком.

## Что из i3 стоит перенять (и уже положить в ROADMAP)

- **автоукладка по правилам** (аналог `assign`) — окно само встаёт в свою зону;
- **пересборка раскладки** при закрытии/перемещении окна (режим `reflow`);
- **вкладки/стопки внутри зоны** — не хватает при 4-5 приложениях на одном месте;
- **scratchpad** — «вызвать окно в зону по клавише и убрать обратно»;
- **критерии по классу и заголовку** для правил и исключений;
- **IPC/демон** — чтобы хоткеи не спавнили процесс Python и чтобы внешние скрипты могли спрашивать
  «что в зоне» и «положи туда»;
- **конфиг как код и профили** — экспорт/импорт сеток и правил.

Что перенять **не** надо: отказ от панели/апплетов и ручной сборки окружения — именно это людям
в Cinnamon и нравится; GridSnap не должен превращаться в «ещё один WM».
